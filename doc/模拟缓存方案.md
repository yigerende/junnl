# 模拟缓存功能方案

## 背景

junnl 当前已有一套基于 SHA-256 前缀指纹的本地 prompt cache 追踪机制（`src/anthropic/cache_tracker.rs`），它会真实跟踪请求前缀的复用情况来计算 `cache_read_input_tokens` 和 `cache_creation_input_tokens`。

但在某些场景下（如对接 new-api 等计费系统），需要能自定义控制返回给下游的缓存数值，类似 WindsurfAPI-2kai 的"cache optimizer"功能。

## 目标

1. 在 admin-ui 增加"模拟缓存"页面，提供完整的配置界面
2. 增加一个总开关：关闭时走原有的真实缓存追踪逻辑，开启时用模拟值替换下游响应中的缓存字段
3. 后端只在最终返回下游时替换 usage 中的缓存字段，内部请求逻辑和 token_manager 完全不动

---

## 第一步：前端页面

### 1.1 导航改造

当前 admin-ui 是单页面（Dashboard），没有路由。需要增加顶部导航 Tab：

- **凭据管理**（当前 Dashboard 内容）
- **模拟缓存**（新页面）

在 header 区域加 Tab 切换，用 React state 控制当前显示的页面，不引入 router 库。

### 1.2 模拟缓存页面内容

从 WindsurfAPI-2kai 搬过来的配置项：

#### 总开关
- **模拟缓存开关**（Switch 组件）
  - 关闭：按原有 `cache_tracker.rs` 的真实缓存逻辑返回
  - 开启：按本页面配置的规则替换下游响应的缓存字段

#### 改写模式（下拉选择）
| 模式 | 说明 |
|------|------|
| `passthrough` | 原样返回（等同开关关闭） |
| `zero` | 缓存读写都返回 0 |
| `cap` | 超过最大值就压到最大值 |
| `random` | 按范围均匀随机 |
| `weighted` | 先按权重抽形态，再随机数值 |

#### 基础参数
- 缓存读最小值（readMin，默认 300）
- 缓存读最大值（readMax，默认 1200）
- 缓存写最小值（writeMin，默认 0）
- 缓存写最大值（writeMax，默认 500）

#### 权重参数（weighted 模式）
- 只读权重（weightReadOnly，默认 55）
- 只写权重（weightWriteOnly，默认 15）
- 读写都有权重（weightReadWrite，默认 30）
- 都不显示权重（weightNone，默认 0）

#### 分段权重（可选）
- 启用分段权重开关（useSegmentWeights）
- 缓存读分段（3 段，每段 min/max/weight）
- 缓存写分段（3 段，每段 min/max/weight）

#### 其他选项
- 只在上游有缓存字段时改写（rewriteOnlyWhenPresent，默认 true）
- 保留原始缓存值到响应中（keepRawBreakdown，默认 true）

#### 实时预览
- 根据当前表单值，模拟一次计算并展示预览结果（假设上游返回 cacheRead=16511, cacheWrite=4800 时，改写后的值是多少）

### 1.3 页面交互

- 页面加载时从后端 GET 当前配置
- 修改后点"保存"提交到后端，下次请求立即生效
- 提供"刷新"按钮重新拉取当前配置

## 第二步：后端实现

### 2.1 配置存储

在 `config.json` 中增加 `cacheOptimizer` 字段：

```json
{
  "cacheOptimizer": {
    "enabled": false,
    "mode": "weighted",
    "readMin": 300,
    "readMax": 1200,
    "writeMin": 0,
    "writeMax": 500,
    "weightReadOnly": 55,
    "weightWriteOnly": 15,
    "weightReadWrite": 30,
    "weightNone": 0,
    "useSegmentWeights": false,
    "readSegments": [
      { "min": 90000, "max": 110000, "weight": 35 },
      { "min": 110001, "max": 130000, "weight": 45 },
      { "min": 130001, "max": 145000, "weight": 20 }
    ],
    "writeSegments": [
      { "min": 20, "max": 200, "weight": 55 },
      { "min": 201, "max": 800, "weight": 35 },
      { "min": 801, "max": 3000, "weight": 10 }
    ],
    "rewriteOnlyWhenPresent": true,
    "keepRawBreakdown": true
  }
}
```

### 2.2 Admin API 新增接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/admin/cache-optimizer` | 获取当前模拟缓存配置 |
| PUT | `/api/admin/cache-optimizer` | 更新配置，持久化到 config.json |

### 2.3 缓存改写逻辑

junnl 返回给下游的 usage 本身已经是标准 Anthropic 格式，兼容 new-api / sub2api / one-api 等所有下游系统，不需要做任何字段适配。只需要在现有的 `CacheUsageBreakdown` 构造完成后、写入响应之前，直接替换其中两个值：

```
if cacheOptimizer.enabled && mode != "passthrough" {
    cache_usage.cache_read_input_tokens = rewritten_read
    cache_usage.cache_creation_input_tokens = rewritten_write
    // cache_creation 子对象 (5m/1h) 也相应调整或置零
}
```

具体介入点：
- **流式响应**：`src/anthropic/stream.rs` 的 `generate_final_events()` 中，在 `cache_usage` 被写入 `message_delta` 事件之前
- **非流式响应**：`src/anthropic/handlers.rs` 的 `inject_cache_usage_fields()` 调用之前
- **buffered 模式**：`src/anthropic/stream.rs` 的 `/cc/v1/messages` 最终拼装 `message_start` 之前

**关键原则：只动最终输出的两个数值字段，不动内部逻辑**

- `cache_tracker.rs` 继续正常运行（指纹追踪、TTL 统计不丢失）
- `token_manager` 内部的调度、凭据选择逻辑不受影响
- 内部请求上游的方式、header、参数完全不变
- 只是最终给下游的 `cache_read_input_tokens` 和 `cache_creation_input_tokens` 被替换成模拟值

### 2.4 改写算法（移植自 WindsurfAPI-2kai）

```rust
fn rewrite_cache_usage(raw_read: u64, raw_write: u64, config: &CacheOptimizerConfig) -> (u64, u64) {
    match config.mode {
        "zero" => (0, 0),
        "cap" => (raw_read.min(config.read_max), raw_write.min(config.write_max)),
        "random" => (rand(config.read_min..=config.read_max), rand(config.write_min..=config.write_max)),
        "weighted" => {
            // 1. 按权重抽形态 (readOnly / writeOnly / readWrite / none)
            // 2. 根据形态决定哪个字段有值
            // 3. 有值的字段按范围随机（或分段加权随机）
        }
    }
}
```

## 注意事项

1. **开关关闭 = 完全透明**：不影响现有任何逻辑，cache_tracker 正常工作
2. **开关开启 = 只改最终输出**：内部 token_manager、凭据调度、cache_tracker 统计全部照旧
3. **配置热更新**：PUT 保存后立即生效，不需要重启服务
4. **不引入额外依赖**：Rust 端用已有的 `fastrand` crate 做随机数
