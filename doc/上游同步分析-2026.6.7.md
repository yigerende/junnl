## 二、`903ff21` 改了什么（按价值排序）

这次提交**以 bug 修复为主**，修的是会导致整类账号无法使用的硬伤，不是单纯加功能。

### 核心 bug 修复（优先级高）

1. **Builder ID 占位 ARN 不再塞进流式请求**（`credentials.rs` + `ide.rs`）
   - 占位 ARN `...638616132270:profile/AAAACCCCXXXX` 不是有效 profile，
     Builder ID 账号携带它请求会被上游拒绝。
   - 新增 `resolved_stream_profile_arn()`：流式生成时占位符返回 None，
     配合 `inject_profile_arn` 在 ARN 为 None 时主动从 body 删除已存在的 profileArn 字段。

2. **usage-limit 重试重写**（`token_manager.rs`）
   - region 兜底：`eu-central-1` / `us-east-1` 互为 fallback。
   - profileArn 兜底：IdC 一律不带；social 带显式 ARN 再加一个不带的兜底。
   - usage 查询写死用**旧版 CodeWhisperer Streaming UA**（`...streaming#1.0.18 ... KiroIDE-0.6.18`），
     否则 Enterprise token 会被拒为 "Invalid profileArn"。
   - `get_usage_limits()` 改为 region × profileArn 双重循环重试。

3. **snake_case 凭据兼容**（`credentials.rs`）
   - 所有字段加 `#[serde(alias = "snake_case")]`，
     Windows IdC 导出的 snake_case 凭据文件可直接导入。

4. **Enterprise / External IdP 路由分流**（`ide.rs`）
   - Enterprise 认证的流式生成走 `codewhisperer.{region}.amazonaws.com`，其余走 `q.{region}`。
   - region 折叠：`eu-` 开头 → `eu-central-1`，其余 → `us-east-1`。
   - 新增 token type 头：API Key → `tokentype: API_KEY`，External IdP → `TokenType: EXTERNAL_IDP`。

### 可选新功能（看二开是否需要）

- **动态模型发现**：`provider.rs` 的 `list_available_models()`（5 分钟缓存 + 分页），
  `/v1/models` 优先返回动态列表，失败回退静态列表。
- **profileArn 自愈**：运行时调 `ListAvailableProfiles` 拿真实 ARN 并写回凭据文件。
- **balanced 会话亲和**：`token_manager.rs` 新增 `session_affinity`（TTL 2h），
  同一 conversationId 复用同一凭据，避免对话在账号间漂移。
- **未来模型名直传**：`converter.rs` 的 `normalize_direct_kiro_claude_model()`，
  支持 `claude-sonnet-4-7` / `claude-opus-5.0-thinking` 等未来版本名归一化。

## 四、必须盯的三个行为变更

1. **IdC 专属 UA / agent-mode 被删** —— 上游统一成 `vibe`，删了 idc 的 spec 模式和
   `aws-sdk-rust ... AmazonQ-For-CLI` 风格 UA。二开若依赖 spec 或自定义 UA，这是回退点。
2. **`persist_credentials` 回写条件放宽** —— 单凭据格式现在**也会回写文件**。
   与二开的并发自适应/凭据回写逻辑语义可能打架。
3. **IdC 响应不再同步 profileArn** —— 改成运行时自愈。二开若读这个字段要注意。

## 五、合并决策

**是否值得合，取决于使用的 Kiro 账号类型：**

- 主要用 **Builder ID / IdC / Enterprise 账号** → **强烈建议合**，
  这次修的就是这些账号的致命 bug（登录后请求被拒 / usage 查不到 / Enterprise 走不通）。
- 只用 **Social（GitHub/Google）账号** → 价值小，Social 路径上游基本没动，可暂缓。

### 推荐两步走（不建议直接 `git merge`）

直接整体 merge 会在 3 个核心文件炸冲突，`token_manager.rs` 尤其危险。更稳的做法：

1. **低风险先合**：第一档 + `credentials.rs`（snake_case 兼容 + ARN 解析），
   拿到 Builder ID/Enterprise 核心 bug 修复，基本不碰二开。
2. **高风险手工挪**：`token_manager.rs` / `provider.rs` 里的 bug 修复逐块 cherry-pick 式手工对齐，
   而非整文件合并。

### 操作建议

- 在**临时分支**上做完整合并、解冲突，`master` 保持不动；
  review 满意后再决定是否采纳。
- 合并后**务必跑真实账号路径**（Builder ID / Enterprise / Social 三类的
  流式 + usage + models），因为上游这批改动全部 live 网络路径未实测。

### 关键修正：隔离性并非"天然"，profileArn 自愈加了二开保护门控

Step 0 逐行核实上游代码，结论修正了"天然隔离"的假设：

- **企业版 modelId 解析**：上游完整包在 `if is_enterprise_auth()` 内，块外仅 `let body`→`let mut body`（纯可变性），对非企业账号是**真 no-op**。✅
- **profileArn 自愈**：上游**仅按 `should_fetch_profile_arn()` 门控**，对任何缺真实 ARN 的账号（含 social）都会触发一次 ListAvailableProfiles 网络请求 —— **不是天然隔离**。
  - **二开保护措施**：移植时**额外加了 `is_enterprise_auth() || is_idc_auth()` 门控**。这样 social 等账号即使缺 ARN 也保持完全 no-op，绝不触发额外网络请求、不进入新代码路径。这是对上游的有意偏离，目的是保护既有调度路径。
