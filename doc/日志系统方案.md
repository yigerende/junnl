# junnl 日志系统方案

## 背景

当前用户报错时（例如 `socket connection was closed unexpectedly`、"容易停"、导入验活失败），
我们很难定位原因，因为：

- junnl 现在只用 `tracing_subscriber::fmt().init()` 把日志打到 **stdout/stderr**，
  正式环境靠 `stdout.log` / `stderr.log` 重定向收集。
- 日志**没有落盘按天滚动**，重启或时间一长就难追溯。
- 日志**没有 requestId 串联**，一次请求横跨 `post_messages → call_api_stream →
  create_sse_stream` 多个函数，出错时无法把同一请求的所有日志捞出来。
- 日志**不是结构化的**，无法按 model / 凭据 / 路由 / 错误类型筛选。
- 流式请求**没有生命周期记录**：什么时候开始、上游首字节多久到、发了几个
  ping、最后是正常结束还是被断开、断开原因是什么——这些全都没有。

参考 `WindsurfAPI-2kai` 项目（`src/dashboard/logger.js`、`src/chat-trace.js`、
`src/sse-registry.js`）已经验证过的日志设计，移植到 junnl（Rust / tracing 技术栈）。

---

## 目标

1. 日志**默认落盘**，按天滚动，保留结构化字段，方便 grep / jq 排查。
2. 每个请求分配 **requestId**，贯穿整条链路；用户报错时只要给一个 requestId
   或时间点，就能捞出该请求的全部日志。
3. **流式请求全生命周期可观测**：记录开始、上游首字节延迟、ping 次数、结束原因
   （正常 / 上游断 / 客户端断 / 超时），直接对应"容易停"类问题。
4. **前端实时面板**：admin 页面实时滚动看日志、按 requestId / level 筛选，内存缓冲
   5000 条（对标 Windsurf），不用进容器 grep。
5. **不拖慢请求**：落盘走非阻塞 writer，基础日志只记元数据字段（不落盘 token / prompt）。

---

## 一、落盘 + 按天滚动（基础层）

### 依赖

`Cargo.toml` 新增：

```toml
tracing-appender = "0.2"
```

`tracing` / `tracing-subscriber` / `serde_json` / `chrono` / `uuid` 已存在，无需新增。

### 初始化改造（`src/main.rs`）

把现在的：

```rust
tracing_subscriber::fmt()
    .with_env_filter(EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("info")))
    .init();
```

改为「**控制台 + 文件**双输出」：

- 控制台层：保留现有人类可读格式（pm2 / docker logs 仍可看）。
- 文件层：写到 `logs/app-YYYY-MM-DD.jsonl`，**JSON 格式**（`.json()`），按天滚动
  （`tracing_appender::rolling::daily`）。
- 文件层用非阻塞 writer（`tracing_appender::non_blocking`），避免磁盘 I/O 拖慢请求。

日志目录：默认项目根下 `logs/`，可用环境变量 `JUNNL_LOG_DIR` 覆盖。

> `logs/` 需加入 `.gitignore`（运行时产物，不进仓库）。

### 日志级别

沿用 `RUST_LOG` 环境变量（`EnvFilter`）。默认 `info`。排查时可临时 `RUST_LOG=debug`。

## 二、requestId 全链路追踪（关键）

### 思路

利用 `tracing` 的 **span** 机制，在请求入口创建一个带 `request_id` 字段的 span，
该请求内所有 `tracing::info!/warn!/error!` 自动带上这个字段，无需手动透传。

### 介入点

在每个 HTTP 入口（`post_messages`、`post_messages_cc`、`count_tokens`、
`get_models`、admin 的 `add_credential` 等）函数开头：

```rust
let request_id = format!("r_{}", uuid::Uuid::new_v4().simple().to_string()[..10].to_string());
let span = tracing::info_span!("request", request_id = %request_id, route = "/v1/messages");
let _guard = span.enter();
```

或更简洁地用 `#[tracing::instrument]` 宏（自动建 span）。

之后该请求链路里 `call_api_stream`、`create_sse_stream`、重试循环等所有日志，
JSON 里都会带 `request_id`，排查时：

```bash
jq 'select(.span.request_id=="r_xxxxxxxxxx")' logs/app-2026-06-07.jsonl
```

就能拿到这条请求从入口到结束的完整时间线。

### 下游可见（可选）

把 `request_id` 通过响应头 `x-junnl-request-id` 返回给下游（new-api / CC）。
这样用户报错时把这个 id 发过来，我们能精确定位，无需在海量日志里靠时间猜。

## 三、流式请求生命周期日志（直击"容易停"）

在 `create_sse_stream` / `handle_stream_request` 链路打点，记录每条流式请求的关键节点：

| 节点 | 字段 | 用途 |
|------|------|------|
| 请求进入 | `request_id`, `model`, `stream=true` | 起点 |
| 选中凭据 | `credential_id`, `attempt` | 定位是哪个账号 |
| 上游连接建立 | `upstream_connect_ms` | 连接耗时 |
| **上游首字节到达** | `upstream_first_byte_ms` | **静默窗口**关键指标 |
| 每次发 ping | 累计 `ping_count` | 保活是否在工作 |
| 上游正常结束 | `reason=upstream_done`, `total_ms`, `output_tokens` | 正常路径 |
| **上游读错误** | `reason=upstream_error`, `error` | 上游断/超时 |
| **客户端断开** | `reason=client_gone` | 下游主动断 |
| **整体超时触发** | `reason=timeout`, `elapsed_ms` | 命中 reqwest `.timeout()` |

落一条 `event=stream_end` 的汇总日志，包含 `reason` + 各项耗时。这样"容易停"
出现时，一眼能看出是 **上游迟迟不返回首字节**、还是 **上游中途断**、还是
**命中 720s 总超时**（即之前定位到的根因）。

> 这一节落地后，再回头评估流式超时改造（`http_client.rs` 的 `.timeout()` →
> `connect_timeout` + `read_timeout`），就能用真实数据验证效果，而不是猜。

## 四、前端实时日志面板（admin-ui）

对标 Windsurf 的 dashboard 实时日志：admin 页面能实时滚动看到日志，并按
requestId / level 筛选，不用进容器 grep。

### 与现有 call-log 的关系

junnl 现在已有「调用日志」页（`admin-ui/src/components/call-log.tsx` +
后端 `src/anthropic/call_log.rs`），但它：

- 存内存 `VecDeque`，默认 **1000 条**，**不落盘**，重启即丢；
- 只记调用概要（模型 / 端点 / 时间），**没有 requestId、没有流式结束原因、没有错误细节**；
- 前端是「手动点刷新拉 1000 条」，**没有实时推送**。

本方案在此基础上增强，不另起炉灶：

1. **内存缓冲扩到 5000 条**（对齐 Windsurf）。
   - 现有 `call_log.rs` 的 `DEFAULT_CAPACITY` 从 1000 → **5000**。
   - 约占 2-5 MB 内存，覆盖约 0.5-1 小时调用历史。
   - 背景：下游多人打并发时，1000 条几分钟就被刷没，截图过来往往只剩末尾，
     看不到出错请求最初的入口日志。5000 条能覆盖完整一轮排查窗口。
   - 容量仍可通过现有 `/api/admin/call-logs/capacity` 接口调整（上限 100000）。

2. **日志条目补充结构化字段**：`request_id`、流式 `reason`（正常/上游断/客户端断/
   超时）、各项耗时、`credential_id`、错误信息。让前端能按 requestId 归类、按
   错误类型筛选。

3. **实时推送（SSE）**：新增 `GET /api/admin/logs/stream`，admin 页用 `EventSource`
   订阅，新日志实时滚动展示（对标 Windsurf 的 `subscribeToLogs`）。
   - 不再依赖手动点刷新。
   - 订阅推送异步 fan-out，不阻塞日志写入主路径。

### 两层存储的分工（重要）

| | 内存环形缓冲 | 落盘 JSONL |
|--|------------|-----------|
| 用途 | 前端实时面板看「最近」 | 事后翻「历史」 |
| 容量 | **5000 条**（约 0.5-1 小时） | 按天滚动，留 **14 天** |
| 重启后 | 丢失 | 保留 |
| 访问 | admin 页面实时滚动 / 筛选 | 容器内 grep / jq |

两者数据同源（同一条日志同时进内存缓冲和落盘 writer），互为补充：前端看实时、
文件查历史。5000 条只决定「前端能往回翻多久」，不影响磁盘上的 14 天历史。

## 五、性能影响与强制约束

加日志的前提是**不能拖慢用户请求**。本方案各项的开销：

| 项 | 开销 | 说明 |
|----|------|------|
| requestId / span（第二节） | 纳秒~微秒级 | 纯内存操作 + 一次 UUID，无 I/O |
| 流式生命周期打点（第三节） | 可忽略 | 每条流式请求多几条内存入队日志 |
| 落盘写文件（第一节） | **不阻塞请求** | 用 `non_blocking` writer，请求线程只入内存 channel，磁盘写由后台线程做 |

实施时**必须**遵守以下硬性约束，否则会反过来拖慢请求：

1. **文件落盘必须用 `tracing_appender::non_blocking`**，绝不能在请求线程里同步写盘。
2. **non_blocking 用 lossy 模式（默认）**：channel 满时丢日志，而不是反压阻塞请求线程。
3. **生产默认 `info` 级别**，不要默认开 `debug/trace`（高频打点会刷爆 channel、抬高 CPU）；
   排查时再用 `RUST_LOG=debug` 临时开。
4. **基础日志不打印请求体 / 完整 prompt**，只记结构化字段（model、credential_id、耗时、
   reason 等），既避免敏感信息落盘，也避免大文本序列化成本。

按以上约束，正常 info 级别下每条日志开销约微秒级，请求端到端延迟增加 <1ms，
相对 junnl 一次动辄数秒至数分钟的请求可忽略。

> 注：本方案**不做**全量请求体追踪（messages/tools 落盘）。基础日志只记元数据字段，
> 不涉及 token / prompt 内容，因此无需额外的脱敏链路。

## 六、日志清理 / 留存

- 按天滚动后，旧文件需定期清理，避免磁盘占满。
- 方案：启动时 + 每天清理一次，删除 `logs/` 下超过 N 天（默认 14 天）的
  `app-*.jsonl` / `error-*.jsonl`。
- 留存天数用环境变量 `JUNNL_LOG_RETAIN_DAYS` 控制，默认 14。

## 八、实施顺序建议

按价值和风险递增分阶段，每阶段独立可上线：

1. **第一阶段（基础落盘）**：第一节 + 第六节。最低风险，立刻让正式环境有
   按天滚动的结构化日志可查。
2. **第二阶段（requestId + 流式生命周期）**：第二节 + 第三节。这是定位
   "容易停 / socket 断"的核心，价值最高。
3. **第三阶段（前端实时面板）**：第四节。扩内存缓冲到 5000 条 + SSE 实时推送 +
   按 requestId 筛选，让排查不用进容器。

> 高风险链路（relay 流式、扣费、凭据）只**新增日志打点**，不改动原有控制流，
> 符合"嵌入式 / 外挂式"低侵入原则。

---

## 注意事项

1. 日志文件落盘用**非阻塞 writer**，不能因为磁盘慢拖垮请求主链路。
2. `logs/` 不进 Git；基础日志只记元数据字段，不落盘 token / prompt 内容。
3. `request_id` 只用于内部排查，回写响应头是可选项，需确认不影响下游解析。
4. 前端实时面板内存缓冲 5000 条仅供「看最近」，历史以落盘文件为准（留 14 天）。
