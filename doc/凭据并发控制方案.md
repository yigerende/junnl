# junnl 凭据并发控制方案（轻量内存版 v2）

> 本版结合了对 junnl 现有调度代码的精读、对 sub2api（Go + Redis 多实例并发方案）机制的借鉴，以及正式环境实测暴露的"踩踏"问题重写。
> 核心修订：**新增 least-active 选号 + 平手随机打散，作为最高优先级机制**；并发硬上限降级为第二层兜底；并发计数放进程内存（不上 Redis）。

---

## 一、背景与真实病根

### 1.1 现象（正式环境实测）

balanced（均衡）模式下，几百并发涌入时，请求**集中砸到 2 个凭据**（成功次数最少的那两个），导致这两个被上游限流（429）、触发重试、整体变慢；而另外 3 个凭据**几乎闲置**。表面看像"凭据不够"，实则是调度算法问题。

### 1.2 根因（精读代码确认）

balanced 选号的依据是 `success_count` 最少者：

```
src/kiro/token_manager.rs:811-813
let entry = available.iter().min_by_key(|e| (e.success_count, e.credentials.priority))?;
```

两个致命点：

1. **计数滞后窗口**：`success_count` 不是在"选中凭据"时 +1，而是在"上游返回响应头"时由 `report_success` 才 +1（`provider.rs:498`）。几百并发瞬间打进来时，第 1 个请求选了 success_count 最小的 A，但 A 的计数还没 +1，第 2…第 N 个请求看到 A 仍然最小，**全部涌向 A**。等 A 的计数追上来，已经堆了几十上百个请求。

2. **选号确定性、平手不打散**：`min_by_key` 是确定性的，平手时永远返回迭代到的第一个。并发请求读到同一份快照 → 全选同一个。

> 这与 sub2api 的分析完全印证：sub2 防踩踏靠两招——**①原子试抢（占不到立刻换下一个）②负载/优先级相同的一组组内随机打散**。junnl 恰好这两招都没有。

### 1.3 目标

- **首要目标（治本）**：消除高并发踩踏，让负载按"当前真实在途数"自动摊平到所有可用凭据。
- **次要目标（兜底）**：可给每个凭据设并发硬上限，满载跳过/短等待/繁忙，保护上游不被打爆。
- 前端凭据卡片实时显示 `当前并发 / 上限` 和等待数。
- **保持轻量**：junnl 是单实例反代，不上 Redis、不做多实例全局并发、不做长队列、不做复杂评分。

### 1.4 明确不做

- 不用 Redis，不做多实例全局并发（sub2 那套 ZSET+Lua 是为水平扩展，junnl 用不上）。
- 不做 sub2 的 5 维评分（优先级/负载/队列/错误率/TTFT）+ Top-K 加权随机——太重。
- 不做长等待队列、不做流式等待期独立 SSE ping 机制（复用现有 25s ping）。
- **不碰 429 限流重试逻辑**（`provider.rs:590-608` 瞬态退避重试）。这块现状很好，并发控制与它完全正交，一行不动。
- 不做用户并发、分组并发、RPM、窗口费用。

## 二、junnl 现有架构（关键事实，精读确认）

调度核心在 `src/kiro/token_manager.rs`：

- `MultiTokenManager`（行 589）：`entries: parking_lot::Mutex<Vec<CredentialEntry>>`、`current_id`、`load_balancing_mode`、`session_affinity` 均为同步 `parking_lot::Mutex`（**持锁期间不可 await**）；唯一可跨 await 的是 `refresh_lock: TokioMutex`。
- `CredentialEntry`（行 471）：`id / credentials / failure_count / refresh_failure_count / disabled / disabled_reason / success_count / request_count / last_used_at`。注意 `request_count` 是**只增不减**的累计量，不能当并发数用。
- `select_next_credential`（行 791）：持 `entries` 锁，过滤可用，balanced 按 `(success_count, priority)` 取 min，priority 按 `priority` 取 min。**确定性、无随机、无在途感知**。
- `acquire_context_for_session(model, session_key)`（行 921）：选号总入口，内含重试循环。选中后调 `try_ensure_token` 刷 token，返回 `CallContext{id, credentials, token, session_affinity_hit}`。
- 锁顺序统一为 **entries → current_id**；`select_next_credential` 额外有 **entries → load_balancing_mode**（嵌套）。所有 `report_*` 在释放锁后才调 `clear_session_affinity_for_credential`（避免与 session_affinity 锁嵌套）。
- `provider.call_api_with_retry`（`provider.rs:416`）：拿 ctx → 发上游 → **响应头一到即 `report_success` 并 `return ApiCallResult{response, credential_id, session_affinity_hit}`，此时 body（流式/非流式）尚未读取**。

**关键难点（与 sub2 一致的语义）：流式请求的"结束"时机。**
`call_api_with_retry` 返回 `ApiCallResult` 时，流式响应只拿到 header，真正读完是在 `handlers.rs` 的 `create_sse_stream` / `create_buffered_sse_stream` 走到 `stream_end`（`handlers.rs:1051/1851` 等）。所以**并发槽位必须从"选中凭据"一直占用到"流读完"**，不能在 `call_api_with_retry` 返回时就释放。sub2 的做法是 `Forward()` 阻塞到流结束才 release——junnl 用 Rust 的 RAII guard 实现等价语义，且更可靠（panic/断开也释放）。

## 三、整体设计

设计分两层，**第一层是治本的核心，第二层是可选兜底**：

- **第一层（必做，解决你当前的踩踏）**：least-active 选号 + 平手随机打散。
- **第二层（可选，默认不开）**：并发硬上限 + 满载跳过/短等待/繁忙。

两层都依赖同一个基础设施：per-credential 在途计数 + RAII guard。

### 3.1 在途计数：放进 CredentialEntry（不单独建锁，不上 Redis）

给 `CredentialEntry` 新增两个字段（运行时态，不持久化）：

```
struct CredentialEntry {
    // ... 现有字段 ...
    active: u32,    // 当前在途请求数（选中即 +1，guard drop 时 -1）
    waiting: u32,   // 当前等待该凭据释放的请求数（仅前端显示）
}
```

**为什么放 entry 而不是单独建 `ConcurrencyState`（v1 文档的写法）？**
1. **原子性**：选号和 `active += 1` 必须在**同一把 `entries` 锁**内完成，否则又出现 TOCTOU 踩踏窗口（这正是 sub2 用 Lua 脚本把"ZCARD<max + ZADD"做成原子的原因——junnl 用 entries 锁达到同样效果）。分两把锁就有竞态。
2. **零新增锁**：不用把新锁排进 `entries → current_id` 的锁顺序里，没有新死锁源。
3. **轻量**：单实例反代不需要 Redis 的跨进程能力。

> `active` 与 `success_count`/`request_count` 是**完全独立的三个量**：`success_count` 管长期均衡的平手裁决（保持现状）、`request_count` 是累计统计（保持现状）、`active` 管当下真实负载（新增）。三者不互相绑定。

### 3.2 RAII 槽位守卫（ConcurrencyGuard）

```
pub struct ConcurrencyGuard {
    manager: Weak<MultiTokenManager>,  // 或 Arc，避免循环引用用 Weak
    credential_id: u64,
    released: bool,                    // 防重复释放
}
impl Drop for ConcurrencyGuard {
    fn drop(&mut self) {
        // 持 entries 锁，找到该 credential，active = active.saturating_sub(1)
        // saturating_sub 防止下溢；找不到该凭据（已删除）则忽略
    }
}
```

- **守卫在 `acquire_context_for_session` 内部、`active += 1` 的同一处生成**。这样 acquire 自身的所有失败/重试分支（token 刷新失败等）都靠 guard 的 Drop 自动还原槽位，不需要在每个失败分支手写释放。
- **守卫必须一路传到流读完**：`acquire` 返回 `(CallContext, ConcurrencyGuard)` → `ApiCallResult` 带上 guard → handlers 的 `StreamContext` / `BufferedStreamContext` 持有 guard，直到 stream_end 时随上下文一起 drop。
- 非流式：`handle_non_stream_request` 读完响应体后 guard 自然 drop。
- 对应 sub2 的"sync.Once + context.AfterFunc 双保险 + ZSET TTL 兜底"——Rust 的 Drop 一招就覆盖了全部场景（正常结束/出错/客户端断开/panic），且无需 TTL 清理 worker。

> **严禁手动 `active -= 1`**（容易漏掉错误分支造成泄漏或下溢）。释放只能走 Drop。

### 3.3 第一层核心：least-active 选号 + 平手随机打散

改 `select_next_credential` 的 balanced 分支（priority 分支同理加随机打散）：

**balanced 模式新选号 key（三级）：**
1. **主键 `active` 最小**（当前在途最少的优先选）—— 这是治踩踏的核心。
2. 平手按 `success_count` 最小（保持长期均衡）。
3. **再平手则在这一组里随机选一个**（`rand` 打散，对应 sub2 的 `shuffleWithinSortGroups`）—— 防止并发请求读同一快照时全选第一个。

```
// 伪代码（balanced：active 为主键）
let min_key = available.iter().map(|e| (e.active, e.success_count)).min();
let tied: Vec<_> = available.iter()
    .filter(|e| (e.active, e.success_count) == min_key)
    .collect();
let chosen = tied[rand::random_index(tied.len())];  // 平手随机
```

**priority 模式（重要：不改变"优先用高优先级号"的语义）：**
key 必须是 **`(priority, active)`**——**priority 为主键，active 为次键**。即：永远先选优先级最高（priority 数字最小）的那一档，只在**同一优先级档位内**才按 `active` least-active + 平手随机打散。

```
// 伪代码（priority：priority 为主键，仅同档内比 active）
let min_priority = available.iter().map(|e| e.credentials.priority).min();
let same_tier: Vec<_> = available.iter()
    .filter(|e| e.credentials.priority == min_priority)   // 先锁定最高优先级这一档
    .collect();
let min_active = same_tier.iter().map(|e| e.active).min();
let tied: Vec<_> = same_tier.iter()
    .filter(|e| e.active == min_active)
    .collect();
let chosen = tied[rand::random_index(tied.len())];        // 同档内 least-active + 随机
```

> ⚠️ **不要写成 `(active, priority)`**——那会让"低优先级但空闲"的号越过"高优先级但繁忙"的号，违背 priority 模式本意。priority 模式的承诺是"优先用高优先级账号"，active 只在同档内做防踩踏的次级打散。
> **跨档启用低优先级的唯一情形**：仅当开启了 `max_concurrency` 且高优先级档**全部满载**时，满载过滤（§3.4）才会把它们排除，从而落到下一档。不设上限（max_concurrency=0）时，priority 模式永远只用最高优先级档，与现状一致。

**为什么 least-active 能根治**：`active` 在"选中的同一时刻、同一把锁内"就 +1，下一个请求立刻看到新值，没有 `success_count` 那种回报滞后窗口。负载按"当下谁最空"实时摊平。且它对历史 skew 免疫——不管某凭据历史上少用了几千次，只看当下在途，不会再死盯着它灌。

> **这一层单独就能解决你正式环境的问题**，且不依赖任何硬上限配置。建议先上这一层验证效果。

### 3.4 第二层兜底：并发硬上限（可选，默认 0=不限）

每个凭据加一个 `max_concurrency: u32` 配置字段（0 = 不限制），存 `KiroCredentials`（随 credentials.json 持久化，`#[serde(default)]` 兼容旧文件）。

选号时（在 3.3 的候选过滤里追加一步，对应 sub2 的"原子试抢，占不到换下一个"）：

**A. 普通请求（无 session_key 或 priority 模式）：**
1. 候选过滤：**跳过 `max_concurrency > 0 && active >= max_concurrency` 的凭据**（满载不选）。
2. 在未满候选里按 3.3 的 least-active + 随机选。
3. 选中 → 持 entries 锁内 `active += 1`，生成 guard 返回（"选号+占用"原子，对应 sub2 Lua 的原子抢槽）。
4. 所有可用凭据都满载 → **短暂等待**：放锁 → `tokio::time::sleep` → 重新拿锁重试，循环最多 ~2 秒。等待期间对"打算等的那个凭据"`waiting += 1`（前端显示），退出时 -1。
5. 等待超时仍全满 → 返回"繁忙"（HTTP 429，带明确 message）。

**B. 会话绑定请求（balanced + 有 session_key + 命中绑定）—— 见 §3.6 专门讨论。**

### 3.6 粘性会话（session affinity）与并发控制如何共存 ⭐

> 这是整个方案最敏感的部分。粘性会话与 least-active **天然对立**：least-active 想把请求摊到最闲的号，粘性会话想把同一会话**焊死在原号上**（为了上游 KV-cache / prompt 缓存命中）。处理不好会丢缓存（费用、延迟双升）或把单号打爆。

#### 3.6.1 junnl 现有粘性机制（精读确认，本方案不改判定逻辑）

junnl 已按 sub2 思路实现了完整的多级会话判定，**并发控制不碰这套判定**：

- **判定锚点**：`session_key` = 上游 `conversationState.conversationId`（精确字符串匹配，调度层不做内容 hash）。
- **conversationId 的派生（converter.rs，3 层来源，命中即短路）**：① `metadata.user_id` 内嵌的 `session_id`（须为合法 UUID）→ ② HTTP 头候选（按序尝试 `x-session-id`、`x-conversation-id`、`x-claude-code-session-id`，非 UUID 的经 **UUID v5 确定性哈希**映射）→ ③ 随机 UUID 兜底（每次不同，等于不参与粘性）。**没有内容 hash，没有额外兜底层。**
- **绑定存储**：`HashMap<conversationId, {credential_id, last_used_at}>`，TTL 2 小时，惰性 prune，**仅 balanced 模式生效**。
- **命中即短路负载均衡**（`token_manager.rs:968`），不被 select_next_credential 覆盖；绑定号失效（禁用/删除/402/刷新失败）自动清绑回退；每次成功 acquire 都 remember（活跃会话续期）。

#### 3.6.2 sub2 的过载处理（参考，不照抄数字）

sub2 粘性账号满载时（`gateway_service.go:1876-1922`）：抢槽失败 → 查该号等待队列深度 → `< StickySessionMaxWaiting(默认3)` 就排队等原号（超时 `StickySessionWaitTimeout=45s`），等到就用原号（保缓存）；**队列已堵 ≥3 个则放弃亲和、回退负载均衡换号**（丢缓存，会话漂移到新号并重新绑定）。即"宁可短等保缓存，但设队列深度+超时两道闸防无限堆积，堵到阈值才认输换号"。

#### 3.6.3 junnl 的关键洞察：Claude Code 会话基本串行

junnl 主力客户是 Claude Code（`x-claude-code-session-id` 头可证）。**Claude Code 单个会话是串行的**——发一个请求、等响应、再发下一个，同一会话极少真正并发。推论：

- **"单会话焊死打爆单号"在 Claude Code 场景基本不发生**。粘性号的 `active` 大多数时间是 0 或 1。
- 真正的高并发来自**多个不同会话同时打入**——这由 least-active 解决（作用于未命中粘性的新会话选号），**不归粘性管**。
- 因此 sub2 的 45s 长排队对 junnl 是过度设计；junnl 只需很短的等待 + 很小的队列阈值。

#### 3.6.4 junnl 的分阶段策略（核心决策）

**第一阶段（默认，max_concurrency=0 不限）——粘性会话零改动：**
- 没有硬上限 → 粘性号永远"未满" → **过载逻辑根本不触发**。
- 粘性会话命中 → 直接用原号、`active += 1`、返回 guard，**行为与现在完全一致**，零风险。
- least-active + 随机打散**只作用于"未命中粘性"的新会话选号**（select_next_credential 内部）。
- ✅ 这样既解决了多会话踩踏（least-active），又对粘性会话**毫发无损**。**你不必现在就决定那个纠结的取舍。**

**第二阶段（仅当你主动给某些号设了 max_concurrency > 0 才生效）——借鉴 sub2，数字调小：**
1. 绑定号不可用（禁用/删除/失效）→ `clear_session_affinity`，回退 A 流程换号（与现状一致）。
2. 绑定号可用但满载（`active >= max_concurrency`）：
   - **优先只等原号**释放（保缓存），短等待 ~2-3 秒，`waiting[原id] += 1`。
   - 等待超时 **或** 原号等待数已达阈值（建议 **≤ 2**，远小于 sub2 的 3，因为 junnl 量小）→ **放弃亲和，回退 A 流程换号**（不直接报繁忙，避免堵死）。换号后该会话自动 remember 到新号（会话漂移一次）。
3. 绑定号可用且未满 → 直接占用（与现状一致）。

> 取舍明示：放弃亲和会丢上下文缓存命中（重新 prefill，费用+延迟上升）。所以等待阈值设小、超时设短，让多数请求能等到原号，只有原号**严重过载**才认输换号。这些数字在第二阶段实测后再调。
> 第一阶段就把"过载是否触发"的开关交给 max_concurrency：全 0 时第二阶段逻辑是死代码路径，粘性 100% 维持现状。

#### 3.6.5 与等待/退避的实现铁律

> 等待用简单的"放锁 → `tokio::time::sleep` → 重新拿锁重试"轮询。可借鉴 sub2 的指数退避+抖动（初始 ~100ms ×1.5 上限 ~1s + 抖动），junnl 量小，固定 50-100ms 间隔也可接受。**关键铁律：sleep 期间绝不持 entries 锁。** session_affinity 锁与 entries 锁不嵌套（沿用现有顺序）。

### 3.7 前端实时显示

- `CredentialEntrySnapshot`（`token_manager.rs:525`）和 `snapshot()`（行 1616）增加字段：
  - `maxConcurrency: u32`（上限，0=不限）
  - `activeConcurrency: u32`（当前在途）
  - `waitingConcurrency: u32`（当前等待数）
- 前端凭据卡片显示：`并发: 1 / 3`（active / max，max=0 显示 `1 / ∞`），有等待时附 `(等待 2)`。
- 卡片加"设置并发"输入框/按钮（单个）；列表上方加"批量设置并发"按钮。
- 这些字段随凭据列表现有的 30 秒轮询刷新，不需要额外接口。

## 五、与 429 重试的关系（重点澄清）

**并发控制与 429 限流重试完全正交，不碰 `provider.rs` 的重试判定逻辑。** 唯一与 `call_api_with_retry` 的交集是 guard 透传：

- `acquire` 返回值从 `CallContext` → `(CallContext, ConcurrencyGuard)`（多解一个）。
- `ApiCallResult` 加 `slot_guard` 字段。
- 成功 `return` 时把 guard 装进 `ApiCallResult`。

**重试时槽位如何释放**：`ctx` 和 guard 都是 for 循环体内的局部变量。一旦 `continue`（429 退避/402 切号/网络错误退避），循环体结束，**guard 作为局部变量自动 drop → 旧槽位自动释放**。RAII 保证：**不需要在任何 429/重试分支里写一行释放代码**，退避时长、故障转移顺序、限流判定全部零改动。

> sub2 是用 `failover_loop` 的 `excludedIDs` + 429 标记冷却来换号；junnl 保持自己的"瞬态退避重试同号、402 切号"哲学不变。两者机制不同但都正交于并发计数，互不影响。

## 六、关键风险与注意点

1. **槽位泄漏是最大风险**：必须用 RAII guard（Drop 释放），`saturating_sub` 防下溢。严禁手动 `active -= 1`。
2. **守卫生命周期要贯穿流式读取**：流式 guard 不能在 `call_api_with_retry` 返回时 drop，必须随 StreamContext 活到 stream_end。这是最易错的点，重点测"流读完 active 归零""客户端中断 active 归零"。
3. **死锁防范**：`active`/`waiting` 放进 entries，复用现有锁，**不引入新锁**。Drop 里只拿 entries 锁，不嵌套其他锁。等待时**先释放锁再 sleep 再重试**（铁律）。
4. **选号+占用必须原子**：`active += 1` 必须与选号在同一把 entries 锁内完成，否则 TOCTOU 踩踏会回来（这是 least-active 能否生效的命门）。
5. **不侵入计费/relay/缓存逻辑**：并发控制只挂在"选凭据"和"请求生命周期"，不改 usage 解析、扣费、模拟缓存、429 重试。
6. **max_concurrency=0 即不限**：旧凭据默认 0，第二层兜底关闭时行为退化为"只有 least-active 选号"，向后兼容。
7. **success_count 保持不动**：它继续管 balanced 的平手长期均衡裁决，active 管当下负载，两套独立。
8. **粘性会话第一阶段零改动**：max_concurrency 全 0 时，粘性命中路径只多一个 `active += 1`，不触发任何等待/换号，行为与现状完全一致（详见 §3.6.4）。**least-active 只作用于未命中粘性的新会话选号**，绝不覆盖已命中的粘性绑定。

## 七、实施顺序建议

> **交付决策：一次性全交**（least-active 防踩踏 + active 计数 + 硬上限配置 + 单个/批量设置接口 + 前端显示与设置 UI）。下面的"阶段"指实现/自测的推进次序，不是分多次部署——最终一起上线。

1. **基础设施（先做）**：`CredentialEntry` 加 `active/waiting` 字段 + `ConcurrencyGuard`（Drop 释放，`saturating_sub` 防下溢）。
2. **least-active 选号（防踩踏核心）**：`select_next_credential` 改为 —— balanced：`(active, success_count)` + 平手随机打散；priority：先按 `priority` 分档，再在**同优先级档内**按 `active` + 随机打散（**不写成 `(active, priority)`**，详见 §3.3）。先在 max_concurrency 全 0 下验证：高并发下 5 个凭据 active 是否均匀摊开。
3. **guard 贯穿请求生命周期**：`acquire` 返回 `(CallContext, guard)` → `ApiCallResult` 带 guard → StreamContext / BufferedStreamContext 持有到 stream_end drop；非流式读完 body drop。重点测：流读完 / 客户端中断 / 上游报错 active 都归零，无泄漏。**429 重试分支一行不动**（局部 guard 自动 drop 释放）。
4. **硬上限 + 设置接口**：`KiroCredentials` 加 `max_concurrency`（serde default）；满载跳过 + 短等待 + 繁忙；粘性过载放弃亲和（§3.6.4 第二阶段逻辑）；`POST /credentials/{id}/concurrency` + `POST /credentials/concurrency/batch`。
5. **前端（与 4 一起）**：卡片显示 `并发 active/max (等待 n)` + 单个设置输入框 + 列表顶部批量设置按钮；类型与 hooks。

每步 `cargo test` + 手测 active/waiting 计数（可加临时日志打印）。全部通过后一次部署。

> 注意：因为硬上限设置 UI 一次性交付，max_concurrency 可能被设成 >0，所以**粘性会话的过载换号路径（§3.6.4 第二阶段）必须同时就位**，不能留空。但默认值仍为 0（不限），不设上限时该路径是死代码，粘性 100% 维持现状。

## 八、验证要点

每条都要能明确判定"过/不过"，建议加临时日志打印 active/waiting 实测。

**A. 防踩踏（核心目标）**
- [ ] balanced 模式，5 凭据，几百并发打入：观察 active 分布是否均匀摊开（不再集中 1-2 个号）；对比改前/改后的限流重试次数应明显下降。
- [ ] 平手随机：多次重放同一批并发，被选中的"最闲号"应随机分布，不固定第一个。

**B. guard 生命周期 / 无泄漏（最大风险）**
- [ ] 非流式请求正常结束 → 对应凭据 active 归零。
- [ ] 流式请求读到 stream_end 正常结束 → active 归零。
- [ ] 客户端中途断开流（关连接）→ active 归零（不泄漏）。
- [ ] 上游报错（4xx/5xx）→ active 归零。
- [ ] **429 retry 释放旧槽位**：构造首个凭据触发瞬态重试，确认重试 continue 时旧凭据 active 回落、新尝试不叠加；重试次数/退避与改前一致。
- [ ] 压测后静置，所有凭据 active 应全部回到 0（无累积泄漏）。

**C. priority 语义不被改变（你重点关注）**
- [ ] priority 模式 + max_concurrency=0：永远只用最高优先级档，低优先级号 active 始终 0（与现状完全一致）。
- [ ] priority 模式，同优先级多个号：高并发下在该档内按 active 摊开 + 随机，不踩踏。
- [ ] priority 模式 + 高优先级档设了 max_concurrency 且打满：此时才落到下一档；解除满载后回到高优先级档。

**D. 粘性会话**
- [ ] **第一阶段（max_concurrency=0，回归）**：同一 conversationId 连发多请求，全部命中原绑定号；least-active 不干扰粘性；**绑定号不换**；绑定号禁用 → 清绑换号。行为与上线前一致。
- [ ] **第二阶段（开了硬上限）**：原号满 → 短等待原号；等待数超阈值（≤2）或超时 → 放弃亲和换号并重绑新号；原号禁用 → 清绑换号。重点验证 Claude Code 串行会话不会误触发换号。
- [ ] 走随机 UUID 的无状态请求：session_hit 永远 None，直接走 least-active，正确摊开。

**E. 配置与前端**
- [ ] 单个设置 `POST /credentials/{id}/concurrency` 生效；批量 `POST /credentials/concurrency/batch` 生效。
- [ ] 卡片显示 `并发 active/max (等待 n)`，max=0 显示 `∞`；30 秒轮询刷新。
- [ ] 旧 credentials.json（无 max_concurrency 字段）加载正常，默认 0（serde default 兼容）。

**F. 不回归（正交性）**
- [ ] relay 转发 / usage 解析 / 扣费 / 模拟缓存：行为与改前完全一致。
- [ ] 429 限流退避、故障转移、重试次数：与改前完全一致。
- [ ] `cargo test` / `cargo clippy` / `cargo fmt` 全绿；前端 tsc / build 通过。
