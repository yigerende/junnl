# junnl 凭据并发控制方案（轻量内存版）

## 一、背景与目标

下游多个客户端同时打到同一个 Kiro 凭据时，容易触发上游限流（429/排队）。需要给每个凭据加并发上限，**真正在后端限制并发**（不只是前端显示），并在凭据卡片上实时显示 `当前并发 / 上限`（如 `1 / 3`）和等待数。

**明确范围（只做这些）：**
- 每个凭据可单独设并发上限，也可一键批量设所有凭据。
- 后端真实限制：每个请求占用一个槽位，结束释放。
- 普通请求遇到凭据满载 → 跳过选别的空闲凭据；全满 → 短暂等待，仍无空闲 → 返回繁忙。
- 会话（conversation）绑定请求 → 尽量等原凭据释放；超时/队列满 → 返回繁忙，**不切换**；原凭据已失效/禁用 → 清绑定重选。
- 前端卡片实时显示并发状态 + 批量设置。

**明确不做：**
- 不用 Redis，不做多实例全局并发。
- 不做长等待队列、不做流式等待期 SSE ping。
- 不做用户并发、分组并发、RPM、窗口费用等复杂功能。

## 二、junnl 现有架构（关键事实）

调度核心在 `src/kiro/token_manager.rs`：

- `CredentialEntry`（行 471）：每个凭据一条，含 id / credentials / failure_count / disabled 等。
- `acquire_context_for_session(model, session_key)`（行 911）：选凭据的总入口。
  - balanced 模式 + 有 session_key → 优先复用会话绑定凭据（`credential_for_session`）。
  - 否则 `select_next_credential`（行 781）按 priority / least-used 选。
  - 选中后 `try_ensure_token` 刷 token，返回 `CallContext{id, credentials, token}`。
- 会话绑定：`session_affinity`（HashMap<session_key, credential_id>），`remember_session_affinity` / `clear_session_affinity`。
- `provider.call_api_with_retry`（provider.rs 行 409）：拿 ctx → 发上游 → 返回 `ApiCallResult{response, credential_id}`。

**关键难点：流式请求的"结束"时机。**
`call_api_with_retry` 返回 `ApiCallResult` 时，流式响应才刚拿到 header，真正读完是在 `handlers.rs` 的 `create_sse_stream` / `create_buffered_sse_stream` 走到 `stream_end`。所以**并发槽位必须从"选中凭据"一直占用到"流读完"**，不能在 `call_api_with_retry` 返回时就释放。

## 三、整体设计

### 3.1 并发计数器（核心数据结构）

在 `MultiTokenManager` 新增一个并发管理器（纯内存）：

```
struct ConcurrencyState {
    // 每个凭据当前在途请求数
    active: HashMap<u64, u32>,
    // 每个凭据当前等待数（仅用于前端显示）
    waiting: HashMap<u64, u32>,
}
// 用 Mutex 包裹；上限存在每个凭据的配置里（见 3.2）
```

- `active[id]`：该凭据当前占用的槽位数。
- `waiting[id]`：当前在等待该凭据释放的请求数（前端显示用）。
- 上限 `max_concurrency`：见 3.2，0 = 不限。

### 3.2 并发上限配置（持久化）

每个凭据加一个 `max_concurrency: u32` 字段（0 = 不限制）：

- 存在 `KiroCredentials` 里（随 credentials.json 持久化），或单独存一个 `concurrency_limits.json`。
  **推荐存 credentials.json**（跟凭据一起，导入导出自然带上），加 `#[serde(default)]` 兼容旧文件。
- Admin API：
  - `POST /api/admin/credentials/{id}/concurrency` body `{limit: u32}` — 单个设置。
  - `POST /api/admin/credentials/concurrency/batch` body `{limit: u32}` — 一键全部设置。

### 3.3 槽位的占用与释放（RAII 守卫）

定义一个 `ConcurrencyGuard`，**Drop 时自动释放槽位**：

```
pub struct ConcurrencyGuard {
    manager: Arc<...>,   // 指向并发状态
    credential_id: u64,
}
impl Drop for ConcurrencyGuard {
    fn drop(&mut self) {
        // active[credential_id] -= 1
    }
}
```

- 选中凭据并占用槽位时，返回一个 `ConcurrencyGuard`。
- **守卫必须一路传到流读完**：`CallContext` 里带上 guard → `ApiCallResult` 带上 guard → handlers 的 `StreamContext` / `BufferedStreamContext` 持有 guard，直到 stream_end 时随上下文一起 drop。
- 非流式：`handle_non_stream_request` 读完响应体后 guard 自然 drop。
- 这样无论请求正常结束、出错、还是客户端断开，guard 都会 drop → 槽位释放，**不会泄漏**。

> 关键实现点：guard 的生命周期 = 整个请求生命周期。Rust 的 Drop 保证了即使中途 panic/断开也会释放。

### 3.4 选凭据时的并发判断（改 acquire_context_for_session）

在现有选凭据逻辑里插入并发检查，分两种情况：

**A. 普通请求（无 session_key 或非 balanced）：**
1. `select_next_credential` 选出候选时，**跳过 active >= max_concurrency 的凭据**（满载的不选）。
2. 在可用且未满的凭据里按原策略（priority / least-used）选。
3. 选中 → `active[id] += 1`，返回 guard。
4. 如果所有可用凭据都满载 → **短暂等待**（如轮询 50ms × 最多 N 次，总计 ~2 秒）。等待期间 `waiting` 计数 +1（前端显示）。
5. 等待超时仍全满 → 返回"繁忙"错误（HTTP 429 / 503，带明确 message）。

**B. 会话绑定请求（balanced + 有 session_key + 命中绑定）：**
1. 先检查绑定的原凭据是否**可用**（未禁用、未删除、未失效）。
   - 不可用 → `clear_session_affinity`，回退到 A 的普通选择流程。
2. 原凭据可用但 **active >= max_concurrency（满载）**：
   - **只等原凭据释放**（不切别的，避免上下文/缓存丢失）。
   - 短暂等待（轮询，总计 ~2-3 秒，可配），`waiting[原id] += 1`。
   - 等到空位 → 占用，返回 guard。
   - 等待超时 / 等待队列满 → 返回"繁忙"，**不切换凭据**。
3. 原凭据可用且未满 → 直接占用。

> 等待用简单的轮询 + `tokio::time::sleep`，不引入复杂的信号量/通知队列（符合"不做长等待队列"）。

### 3.5 前端实时显示

- 凭据状态接口（`get_all_credentials` / `CredentialEntrySnapshot`）增加字段：
  - `maxConcurrency: u32`（上限，0=不限）
  - `activeConcurrency: u32`（当前在途）
  - `waitingConcurrency: u32`（当前等待数）
- 前端凭据卡片显示：`并发: 1 / 3`（active / max），有等待时附 `(等待 2)`。
- 卡片加"设置并发"输入框/按钮（单个）；列表上方加"批量设置并发"按钮。
- 这些字段是内存实时值，跟随凭据列表的 30 秒轮询刷新（已有机制），不需要额外接口。

## 五、关键风险与注意点

1. **槽位泄漏是最大风险**：必须用 RAII guard（Drop 释放），保证请求中途断开/出错/panic 也能释放。严禁手动 `active -= 1`（容易漏掉错误分支）。
2. **守卫生命周期要贯穿流式读取**：流式请求 guard 不能在 `call_api_with_retry` 返回时 drop，必须随 StreamContext 活到 stream_end。这是实现最易错的点，需重点测试"流读完槽位归零""客户端中断槽位归零"。
3. **等待要短、要有上限**：普通请求等 ~2s，会话请求等 ~2-3s，超时即返回繁忙。绝不做无限等待或长队列（会拖垮服务）。
4. **死锁**：并发状态用独立 Mutex，不要在持有 entries 锁时再拿并发锁（参考现有代码已有的锁顺序注释，行 990）。等待时**不能持锁 sleep**——先释放锁再 sleep 再重试。
5. **不侵入计费/relay 主链路逻辑**：并发控制只在"选凭据"和"请求生命周期"挂钩，不改 usage 解析、扣费、模拟缓存等。
6. **max_concurrency=0 即不限制**：保持向后兼容，旧凭据默认 0（不限），行为和现在完全一致。
7. **重试与槽位**：`call_api_with_retry` 内部重试切换凭据时，要释放旧凭据槽位、占用新凭据槽位（guard 随之转移）。

## 六、实施顺序建议

1. **第一阶段（后端核心）**：并发计数 + guard + 配置字段 + acquire 时的占用/跳过/等待。先不接流式 guard 传递，用非流式验证槽位占用释放正确。
2. **第二阶段（流式生命周期）**：guard 贯穿 StreamContext / BufferedStreamContext 到 stream_end。重点测槽位不泄漏。
3. **第三阶段（会话绑定等待）**：会话命中时只等原凭据、超时返回繁忙、失效清绑定。
4. **第四阶段（前端）**：显示并发状态 + 单个/批量设置。

每阶段 `cargo test` + 手测槽位计数（可加临时日志打印 active/waiting）。

---

## 七、验证要点

- 单凭据设上限 1，并发打 3 个请求：1 个在跑，2 个等待或被拒；前端显示 `1/1 (等待 2)`。
- 请求正常结束 / 客户端中断 / 上游报错：active 都要正确归零（无泄漏）。
- 会话请求：原凭据满 → 等待；超时 → 繁忙且不切换；原凭据禁用 → 清绑定换号。
- max_concurrency=0：行为和加功能前完全一致（回归）。
- 关键链路（relay 转发、计费、模拟缓存）行为不变。
